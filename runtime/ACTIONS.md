Audited repositories: `araru-server`, `araru-web`, `araru-design`, `araru-android`, `araru-desktop`, `araruoss.github.io`, and `araruoss`.

| Repository | Release source | Package/publish gate | Result |

## Required release contract

Distributable repositories must follow this order:

```text
Conventional Commit → release-please PR → version/tag/GitHub release
→ package or publish immutable artifact → deploy → final validation
```

Server and Web currently implement this contract: the publish job depends on the release job and is conditional on a created release. Docker metadata emits the exact version plus major/minor compatibility tags and `latest`; production deployments should pin the exact version.

The current Actions review found no missing package gate for an implemented distributable. Android and Desktop are placeholders with no buildable project, so adding a package job now would produce a misleading artifact. Design has no published package contract. Docs builds and deploys the Pages artifact independently of release creation so documentation changes remain deployable even when they do not produce a version bump.

## Semantic Versioning policy

- `fix` produces a patch release.
- `feat` produces a minor release.
- `!` or `BREAKING CHANGE` produces a major release.
- Each component has an independent version and release cycle.
- Versions must be generated by release-please from Conventional Commits; do not edit release versions manually.
- A failed CI, package, publish, deploy, or artifact validation gate blocks completion and Issue closure.
